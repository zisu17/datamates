# Data Mates

**dbt 위에 올리는 데이터 플랫폼 콘솔.** SQL로 데이터 모델을 정의하고, 그 모델들을 묶어
파이프라인으로 운영하고, 컬럼 단위까지 계보를 추적합니다. 설치형이라 서버 하나만 띄우면
화면과 API가 함께 뜹니다.

dbt를 대체하지 않습니다. dbt가 이미 잘하는 일(의존성 해석, 실행 순서, materialization,
테스트)은 그대로 맡기고, **dbt가 주지 않는 것**을 얹습니다 — 화면, 카탈로그, 컬럼 계보,
파이프라인 운영, 변경 이력.

---

## 무엇을 해결하나

| 상황 | Data Mates에서 |
| --- | --- |
| 이 테이블이 어디서 왔는지 아무도 모른다 | 원천부터 컬럼 하나까지 계보를 그림으로 |
| `amount` 컬럼이 어떻게 계산되는지 SQL을 열어봐야 안다 | 컬럼에 `fx` 표시, 누르면 변환식 |
| 이 모델을 고치면 뭐가 깨지는지 모른다 | 하위 모델 전체를 강조해 영향 범위 확인 |
| 원천이 들어온 걸 알아야 다음 작업을 돌린다 | 데이터가 갱신되면 파이프라인이 자동 실행 |
| 같은 테이블을 두 곳에서 적재해 값이 어긋난다 | 한 모델의 적재는 파이프라인 하나만 — 구조로 차단 |
| 누가 언제 무엇을 바꿨는지 추적이 안 된다 | 저장할 때마다 변경 이력 자동 기록 (SQL은 diff) |

## 세 화면

### 데이터 모델 — 정의하고 계보를 본다

모델 하나 = SQL 하나 = dbt model 하나입니다. 화면 가운데는 항상 **데이터 계보**입니다.

- **모델 관계**가 기본. 헤더의 `+`를 누르면 모든 상자가 **컬럼까지 펼쳐지고** 컬럼 사이
  연결선까지 나옵니다. 배율과 위치는 그대로 — 화면이 옮겨지지 않고 확장됩니다.
- 컬럼을 누르면 **그 컬럼의 전체 경로**가 상·하류로 강조됩니다.
  `raw_events.amount → stg_events.amount → fct_events.amount → agg_daily_events.total_amount`
  처럼 4단계도 한 번에 보입니다.
- 계산된 컬럼에는 `fx`가 붙고, 누르면 실제 변환식과 입력 컬럼이 나옵니다.
  여러 컬럼이 하나를 만드는 N:1도 그대로 표현됩니다.
- 하단 상세 탭: **모델 정보 · SQL · 품질 규칙 · 데이터 미리보기 · 변경 이력**.
  모델 정보는 정의만(저장 위치·구분·생성 방식·설명·사용 파이프라인) 담고,
  나머지는 각 탭이 맡습니다.
- 모델을 선택해 **파이프라인 생성**으로 넘어갑니다. 파이프라인 생성의 유일한 진입점입니다.

FK를 추론해 그리는 ERD가 아닙니다. **SQL의 `ref()`가 만든 실제 데이터 흐름**입니다.

### 데이터 파이프라인 — 묶어서 운영한다

왼쪽은 파이프라인 목록(**다음 실행이 임박한 순** + Pause 토글), 오른쪽은 탭입니다.
IDE처럼 여러 파이프라인을 동시에 열어 비교합니다.

- **파이프라인 흐름** — 파이프라인 사이의 실행 의존성. 연결점을 끌어 「성공 시 실행」을
  잇고, 연결 라벨을 눌러 끊습니다. 순환은 만들 수 없습니다.
- **파이프라인 탭** — 그 DAG의 Task와 실행 상태. `+`로 상류(원천·조회 전용 입력)를
  펼쳐볼 수 있습니다. 여기서 구조는 바꿀 수 없습니다 — 실행 순서는 모델의 `ref()`가 정합니다.
- 실행 방식 네 가지: **예약 · 수동 · 선행 파이프라인 완료 후 · 데이터 이벤트**

### 데이터 품질 — 규칙과 결과

dbt 테스트를 규칙으로 관리합니다. 통과율·위반 내역·모델별 상태를 보고, 규칙을 추가하면
`schema.yml`에 반영됩니다.

---

## 두 층의 의존성

섞이기 쉬운 두 가지를 구분합니다.

```
Task Dependencies      모델 ↔ 모델    데이터 의존성    dbt가 결정, 수정 불가
Pipeline Dependencies  파이프 ↔ 파이프  실행 의존성      사용자가 구성
```

모델 간 흐름은 SQL을 고쳐야 바뀌고, 파이프라인 간 흐름은 화면에서 잇고 끊습니다.
파이프라인을 연결해도 **데이터 의존성은 바뀌지 않습니다** — 트리거 관계만 바뀝니다.

---

## 적재 소유권

**한 모델의 적재는 파이프라인 하나만 맡습니다.** 같은 테이블을 두 파이프라인이 각자
쓰면 값이 어긋나고, 어느 쪽이 맞는지 알 수 없게 됩니다.

이미 다른 파이프라인이 적재하는 모델을 새 파이프라인에 넣으면 **조회 전용 입력**이 됩니다.
읽기만 하고, 적재는 원래 담당이 계속 맡습니다. 조회 전용 카드에는 어느 파이프라인이
적재하는지 표시됩니다.

조회 전용 입력이 생기면 시스템이 먼저 제안합니다 — "그 모델은 A가 적재합니다.
A가 성공하면 이 파이프라인이 이어서 실행되도록 연결할까요?"

---

## 데이터 이벤트

시계가 아니라 **데이터가 방아쇠**입니다. 입력 데이터가 갱신되면 파이프라인이 시작합니다.

감시 대상은 조회 전용 입력 모델과 원천 CSV이고, 여럿이면 **하나만 갱신돼도** 돕니다.

선행 트리거와 다릅니다. 선행 트리거는 앞 파이프라인이 **끝까지** 성공해야 하고,
데이터 이벤트는 **내가 읽는 그 모델**이 갱신되는 순간 반응합니다.

Airflow Asset으로 구현했습니다. 폴링이 아니라 이벤트라, 원천 재적재 후 **1초 안에**
다음 파이프라인이 시작합니다.

---

## 변경 이력

저장할 때마다 자동으로 기록합니다. 따로 커밋하거나 기록을 남기지 않습니다.

- **SQL** — unified diff
- **입력 관계** — `ref()`가 바뀌면 before → after
- 설명 · 생성 방식 · 컬럼 정의 · 태그
- **품질 규칙** — 추가 / 심각도 변경 / 사용·중지 / 삭제

`모델 수정 → 저장 → 변경 이력 자동 생성`

## 정보의 출처

원칙은 하나입니다 — **dbt가 아는 것은 다시 계산하지 않습니다.**

| 정보 | 출처 |
| --- | --- |
| 의존 관계 · 물리 위치 · 생성 방식 · 설명 · 품질 규칙 | dbt manifest (`dbt parse`) |
| 컬럼 타입 | dbt catalog (`dbt docs generate`) |
| 컬럼 단위 계보 · 변환식 | SQL AST 분석 (sqlglot) |
| 실행 상태 · 다음 실행 시각 · Pause | Airflow |
| 파이프라인 정의 · 폴더 · 변경 이력 | 메타스토어 (SQLite) |

관계를 따로 저장하는 곳이 **없습니다.** SQL의 `ref()`를 고치면 카탈로그·계보·파이프라인
DAG가 저절로 따라 바뀝니다.

컬럼 계보는 `dbt compile`을 쓰지 않습니다. 로컬 Spark 기동에 15초가 들어 화면에서 쓸 수
없습니다. 대신 의미가 확정된 Jinja만 직접 치환하고, 매크로처럼 해석할 수 없는 것이 남으면
**추측하지 않고 「계보 확인 불가」로 표시**합니다. 틀린 계보를 보여주는 것보다 모른다고
말하는 편이 낫습니다.

## 구성

저장소 루트는 Data Mates 이고, **dbt 프로젝트는 그 안의 `dbt/`** 입니다.
경계가 곧 소유권입니다 — `dbt/` 안은 dbt 가, 바깥은 플랫폼이 소유합니다.

```
datamates/
├── dbt/                        ← dbt 프로젝트. 데이터 정의의 SSoT
│   ├── dbt_project.yml · packages.yml
│   ├── models/ · seeds/ · macros/ · tests/
│   ├── profiles/               ← DBT_PROFILES_DIR
│   └── target/ · logs/ · dbt_packages/   ← 산출물 (git 제외)
├── datamates/app/              ← FastAPI 서버
├── ui/                         ← 화면 (index.html · app.css · js/)
├── dags/                       ← datamates_*.py 는 파이프라인 저장 시 자동 생성
├── docker/ · scripts/ · tools/
├── docker-compose.yml · env.sh
└── .datamates/datamates.db     ← 메타스토어
```

`env.sh` 가 `DBT_PROJECT_DIR` 을 잡아 두므로 dbt 명령은 **저장소 루트에서 그대로**
쓰면 됩니다 (`dbt build`, `dbt deps` — `cd dbt` 할 필요 없습니다).

| 구성요소 | 버전 |
| --- | --- |
| dbt-core / dbt-spark | 1.12.0 / 1.11.0 |
| PySpark | 4.0.4 (로컬 세션) |
| Airflow | 3.2.2 |
| Iceberg | REST 카탈로그 + MinIO(S3) |
| sqlglot | 30.14.0 |
| DuckDB | 미리보기·통계 조회용 |

데이터 미리보기와 실행 통계는 Spark를 거치지 않고 DuckDB로 Iceberg를 직접 읽습니다.
같은 조회가 **17초 → 0.04초**입니다.

파이프라인 실행은 태스크 하나씩 순차로 돕니다. Iceberg 카탈로그가 SQLite라 dbt 둘이
동시에 커밋하면 깨지기 때문입니다(측정: 순차 3회 오류 0건 / 병렬 2개 매번 14건).
카탈로그를 Postgres로 바꾸면 올릴 수 있습니다.
